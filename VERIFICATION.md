## What each invocation class can get wrong

The four classes fail in different directions, so they are tested differently. A single pass rate hides all of this, which is why coverage is counted per skill below.

| Class | The failure it is prone to | What a passing test looks like |
| --- | --- | --- |
| **Owner** | Two owners run the same phase | Exactly one owner in the fired set, every run |
| **Passive** | Fires instead of the owner, or not at all, or crowds a neighbour | Fires *alongside* an owner on its domain, silent on trivial work, and does not displace the specialist next to it |
| **Conditional** | Fires on the neighbour's trigger, or misses its own | Fires on the precondition, silent on the near-miss phrasing |
| **Manual** | Selectable at all | Absent from the model's skill listing |

## How consolidation was verified

Consolidation means one owner per phase. Three case shapes test it.

**Collision cases** are written so two owners *would* both fit. `pr-hides-a-bug` says "this branch introduces a bug somewhere, review it and find it", which is a review request and a debugging request in one sentence. `take-a-look-at-my-changes` is ambiguous enough to reach any reviewer. `fallback-secret` sits between debugging, review, and three security specialists. Each accepts several owners and fails on more than one.

**Bare-trigger negatives** use the exact phrasing the excluded competitors advertise. `review-pr-bare` is the literal words "review this PR", which upstream Pocock `code-review`, Trail of Bits `differential-review`, Cursor `review-and-ship` and the Vercel pair all claimed before curation. It forbids every one of them.

**Evidence-gated positives** prove the specialist still arrives when it should. `review-auth-pr-security` and `ho-refunds-and-cards` both require the review owner *plus* the security specialist, so narrowing a trigger cannot be mistaken for silencing it.

The runner treats two owners in one session as a hard failure and exits non-zero. The owner set is declared in `eval/run-eval.py`, and skills that are designed to co-run with an owner, such as `diagnosing-bugs`, are deliberately excluded from it.

## How passive skills were verified

Passives are the awkward class. They must fire *with* the owner, never *as* the owner, and never on work too small to need them. One test cannot show that, so each passive gets three.

1. **Does it fire on its domain, with an owner?** `ho-csv-button` requires `react-best-practices` and accepts `ce-work`. Passing means both appear.
2. **Does it stay silent on trivial work?** `string-typo`, `ho-rename-var` and `explain-function` forbid every overlay. A passive that fires here is noise.
3. **Does it leave the neighbouring specialist alone?** `ho-focus-rings` requires `web-design-guidelines` and must not be answered by the React overlay; `ho-eight-booleans` requires `composition-patterns`.

Both passive failures found here were caught by test 1 while tests 2 and 3 stayed green, which is what made them diagnosable: the skills were not over-firing, they were not firing at all. Both had triggers naming the technology rather than the moment. The fixes were re-run against all three tests before being kept, and the negative cases were re-run specifically to prove the widened triggers had not become noisy.

```bash

python3 eval/run-eval.py --corpus eval/heldout.jsonl --runs 2      # different wording
python3 eval/run-eval.py --tag collision --runs 3                  # just the deliberate fights

```

After changing any passive skill's description, run its three tests together. Fixing test 1 by widening a trigger is easy and breaks test 2 quietly.
